SwarmForge Local Tool Handoff

Summary for moving a locally enhanced SwarmForge setup out of a project copy and into a reusable local tool repo.

Goal

The user wants to use the same enhanced SwarmForge implementation across multiple local repos on this Mac: textbee-ops, the TextBee fork repo, and any future projects. The current enhanced copy appears to live inside or near the Bounceoids repo, and was originally installed with a curl-based upstream copy.

Known Current Situation

  • Current working repo for this handoff: /Users/bpappas/Code/GitHub/textbee-ops.
  • Existing modified SwarmForge copy: /Users/bpappas/Code/GitHub/Bounceoids.
  • The Bounceoids copy was installed with curl from unclebob/swarm-forge.
  • Another Codex context has already added feature enhancements to that local copy.
  • That work also pulled newer changes from unclebob/swarm-forge.
  • The user wants those machine-local feature updates available in textbee-ops and the local TextBee fork repo.

Recommended Design

Treat SwarmForge as a separate reusable local tool, not as vendored source inside each project repo. Each project should commit only its own project-specific SwarmForge configuration and prompts. 

/Users/bpappas/Code/GitHub/swarm-forge
  Reusable local clone/fork of SwarmForge itself.
  Holds user feature enhancements and upstream merges.

/Users/bpappas/Code/GitHub/textbee-ops
  Project repo. Holds TextBee ops/devops docs, compose files, runbooks, and project-specific swarmforge config.

/Users/bpappas/Code/GitHub/textbee
  TextBee app fork repo. Holds app code and its own project-specific swarmforge config.
Best approach: extract the enhanced SwarmForge work from the Bounceoids-installed copy into a dedicated swarm-forge repo, then run that one local tool from all project repos.

Why Not Vendor It Into Every Repo?

  • Vendoring creates duplicated tool copies that drift apart.
  • Feature enhancements would need to be copied repeatedly.
  • Upstream pulls from unclebob/swarm-forge become harder to manage.
  • Project repos should remain focused on their own prompts, roles, docs, and source code.

Recommended Linkage

Prefer one user-level launcher on PATH, such as a symlink in ~/bin, instead of committing absolute symlinks inside project repos. 

~/bin/swarm
  -> /Users/bpappas/Code/GitHub/swarm-forge/swarm

Then each project can run the same local SwarmForge implementation:

cd /Users/bpappas/Code/GitHub/textbee-ops
swarm

cd /Users/bpappas/Code/GitHub/textbee
swarm

Project-Local Files To Commit

Each project should commit its own SwarmForge topology and prompt constitution. For textbee-ops, the intended structure is likely: 

swarmforge/
  swarmforge.conf
  constitution.prompt
  constitution/
    project.prompt
    engineering.prompt
    workflow.prompt
  architect.prompt
  coder.prompt
  reviewer.prompt
  devops.prompt

The TextBee app fork can have a similar structure, but its project.prompt and role prompts should focus on app-code work rather than deployment/devops work.

Runtime Paths To Ignore

SwarmForge generates local state, worktrees, logs, and notification helpers. These should not usually be committed: 

.swarmforge/
.worktrees/
swarmtools/
logs/
agent_context/

Suggested Work Plan For Next Codex Context

  1. Inspect the modified Bounceoids SwarmForge copy and identify the exact SwarmForge files present there.
  2. Clone or create the user's fork of unclebob/swarm-forge at /Users/bpappas/Code/GitHub/swarm-forge.
  3. Diff the Bounceoids-installed copy against the clean fork/upstream state.
  4. Port the user's local feature enhancements into the dedicated swarm-forge repo.
  5. Commit those enhancements in the dedicated tool repo.
  6. Create a user-level launcher symlink or shell alias so swarm resolves to the dedicated tool repo.
  7. Add project-specific swarmforge/ config to textbee-ops.
  8. Add a separate project-specific swarmforge/ config to the local TextBee app fork.
  9. Verify both repos launch using the same dedicated SwarmForge tool.

Safety Notes

  • Do not overwrite the Bounceoids copy until its local enhancements are identified and preserved.
  • Do not commit absolute symlinks from project repos to the local SwarmForge tool.
  • Do not commit generated SwarmForge runtime directories.
  • Do not commit secrets from TextBee deployment work.
  • Before first launch in an existing repo, inspect SwarmForge startup behavior for any cleanup intended only for fresh curl-installed directories.

TextBee Context

The textbee-ops repo is intended to be the DevOps/control repo for both local macOS development and TrueNAS production deployment. The TextBee fork repo is expected to hold actual app-code changes. SwarmForge project prompts should preserve that split: 

textbee-ops
  Compose files, Caddy/Cloudflare config, scripts, deployment docs, runbooks, local dev/prod ops workflows.

textbee
  TextBee application source code changes, especially auth changes and frontend/backend app behavior.
